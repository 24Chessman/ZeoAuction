\section*{1. Project Title \& Description}

\textbf{ZeoAuction} is a microservices-based real-time auction platform built on
Service-Oriented Architecture (SOA) principles. Users create, bid on, and settle auctions
across independently deployable services that communicate through Apache Kafka
(event-driven, asynchronous) and REST APIs (synchronous, request--response). Sellers must
complete identity verification (KYC) before they may list; the platform charges a flat
convenience fee on each completed sale; and settlement funds are held by the platform in
escrow for a bounded buyer-protection window, released to the seller only when the window
expires without a dispute or the buyer confirms receipt. The platform is designed to
sustain high concurrent bid throughput with low end-to-end latency, enforce consistency
across service boundaries using the Saga pattern, detect fraudulent bidding behaviour from
a live event stream, and degrade gracefully under partial failure through circuit breakers
and per-service health checks with automatic restart.

\section*{2. Application Type}

Web application with a React 18 single-page frontend and Python (FastAPI) microservices on
the backend. The architecture is hybrid: a documented REST API exposes the same
capabilities to mobile clients and third-party integrators, while WebSocket channels carry
live bid updates. Every backend service is containerised with Docker, runs locally under a
single Docker Compose file, and deploys from the same image as an independent service on
Render; the React frontend deploys to Vercel.

\section*{3. Problem Statement \& Motivation}

\noindent\textbf{Limitations of monolithic, centralised auction systems:}
\begin{itemize}
    \item Write contention on a single hot row (the current auction price) throttles
          throughput as concurrency rises.
    \item Simultaneous equal bids produce ambiguous ordering, so the winner depends on
          client clocks or arbitrary database interleaving.
    \item Outbid notifications delivered by client-side polling arrive several seconds
          late, by which point the bidding window may have closed.
    \item Failure of one subsystem (e.g.\ the payment processor) takes the entire
          application offline.
    \item Fraud patterns such as shill bidding are found in overnight batch analysis,
          hours after the auction has already settled.
    \item Payment is released to the seller on capture, so a buyer who receives nothing,
          or receives an item that does not match the listing, has no recourse inside the
          platform.
    \item Unverified sellers can list anonymously, so a suspended account is recreated in
          minutes and there is no accountable identity behind a listing.
    \item Components cannot be scaled independently: load on payment processing degrades
          bid ingestion.
\end{itemize}

\noindent\textbf{How ZeoAuction addresses each:} authoritative server-side sequencing for
deterministic conflict resolution; Redis-backed write buffering with batched persistence;
WebSocket push instead of polling; per-service horizontal scaling; circuit breakers with
defined fallback behaviour; a streaming fraud detector consuming the same Kafka topic as
the bid pipeline, so detection happens in-flight rather than after the fact; platform-held
escrow with a time-bounded dispute window backed by administrator adjudication; and a
mandatory seller KYC gate enforced at the service layer, so listing is impossible without
a verified identity.

\section*{4. Target Users \& Key Use Cases}

\noindent\textbf{User classes:} individual sellers (hobbyists, small traders), buyers and
collectors, platform administrators (KYC review, moderation, dispute adjudication), and
third-party applications consuming the public REST API.

\medskip
\noindent\textbf{Core use cases:}
\begin{itemize}
    \item A prospective seller registers and submits KYC documents. An administrator
          reviews and approves them. Only then does the listing endpoint accept a request
          from that account; an unverified seller receives an explicit rejection.
    \item A verified seller creates an auction with title, images, reserve price, and
          duration.
    \item A buyer places a bid; the system validates funds and eligibility, resolves it
          against concurrent bids, updates the price, and broadcasts the change to all
          connected watchers. The bid screen discloses the flat convenience fee that will
          be added if the bid wins.
    \item An outbid buyer receives a push alert and counter-bids within the same session.
    \item The fraud service identifies a shill-bidding pattern, flags the auction, opens a
          dispute case, and blocks settlement pending administrator review.
    \item An auction closes; the orchestrator generates an invoice for the winning bid plus
          the flat convenience fee, captures the total, and holds it in platform escrow.
          The seller is notified to ship.
    \item The buyer confirms receipt, which releases the escrowed amount to the seller
          immediately, net of the fee.
    \item The buyer instead raises a dispute inside the protection window, attaching
          evidence. The escrowed funds are frozen, an administrator adjudicates, and the
          outcome is either a refund to the buyer or a release to the seller.
    \item The protection window expires with no dispute and no confirmation. A scheduled
          job releases the funds to the seller automatically, and the dispute option is
          permanently closed for that order.
\end{itemize}

\medskip
\noindent\textbf{Settlement policy (fixed rules the implementation must enforce).}
\begin{itemize}
    \item \textbf{Convenience fee:} a single configured flat amount per completed sale, not
          a percentage of the hammer price. It is disclosed on the bid screen before a bid
          is placed, added to the winning bid at invoice generation, captured with the
          total, and retained by the platform on release. It is non-refundable on a
          buyer-fault dispute outcome and refunded in full when the platform or seller is
          at fault. Losing bidders are never charged.
    \item \textbf{Escrow hold:} the captured total is held by the platform, not forwarded
          to the seller, from capture until release. No code path transfers funds to a
          seller outside the release transition.
    \item \textbf{Protection window:} a configurable duration (default 7 days) beginning
          when the seller marks the item shipped. A dispute may be raised only while the
          window is open; the API rejects a dispute request on a closed window.
    \item \textbf{Release triggers:} buyer confirms receipt (immediate release); window
          expires with no dispute (scheduled automatic release); or administrator
          adjudication resolves an open dispute in the seller's favour.
    \item \textbf{Refund trigger:} administrator adjudication resolves an open dispute in
          the buyer's favour, reversing the capture through the payment provider.
    \item \textbf{Terminal state:} once released or refunded, the order is closed and no
          dispute may be opened against it.
\end{itemize}

\section*{10. Success Metrics}

Load and latency figures are measured against the containerised deployment on a dedicated
8~vCPU / 16~GB host, not on developer laptops. Functional, resilience, and availability
metrics are verified on the live Render and Vercel deployment.

\begin{itemize}
    \item \textbf{Throughput:} sustain 1000 bids per second aggregate across 50 concurrent
          auctions for 10 minutes with an error rate no higher than 0.1\%, and 200 bids per
          second sustained against a \emph{single} auction, which is the contended case
          Section~3 identifies.
    \item \textbf{Latency:} 95th-percentile bid acknowledgement under 500\,ms; 95th-percentile
          WebSocket fan-out from bid acceptance to watcher receipt under 100\,ms, measured
          with 500 concurrent watchers on a single auction.
    \item \textbf{Settlement correctness:} over 1000 simulated settlements, every order
          reconciles exactly --- captured amount equals winning bid plus the flat fee, the
          seller payout equals the captured amount minus the fee, and no order is both
          released and refunded. Zero tolerance: a single reconciliation failure fails the
          metric.
    \item \textbf{Escrow and window enforcement:} no funds release before the protection
          window closes or the buyer confirms; a dispute request against a closed window is
          rejected; the scheduled sweep releases expired holds within 5 minutes of expiry.
          Verified by a time-accelerated test fixture covering every terminal path.
    \item \textbf{KYC gate:} zero auctions created by an account not in the verified state,
          tested directly against the service API rather than through the UI.
    \item \textbf{Resilience:} stopping any one backend service leaves the remaining
          functionality available, and the service returns without manual intervention via
          its container restart policy and Render health check. Verified by a documented
          chaos test per service.
    \item \textbf{Fraud detection:} on a seeded dataset of 500 synthetic auctions containing
          200 labelled shill-bidding rings, achieve recall $\geq$ 0.90 at precision
          $\geq$ 0.75, with alerts raised before auction close.
    \item \textbf{Code quality:} 80\% unit-test coverage on backend services, zero linting
          errors in CI, two approvals required per merge.
    \item \textbf{Effort:} each of the 8 members logs 200 hours; team total 1600 hours,
          tracked weekly.
\end{itemize}

\section*{12. Conclusion}

ZeoAuction exercises the core concerns of service-oriented design: decomposition into
independently deployable services, asynchronous event-driven integration, consistency
across transaction boundaries without distributed locking, real-time stream processing, and
fault isolation. The 1600 person-hour scope divides into eight equal 200-hour allocations,
each anchored to a named component with its own deliverable, so individual contribution is
both substantial and separately assessable.
The technical difficulty sits where it should: in deterministic conflict resolution under
concurrency, in detecting adversarial behaviour from a live stream fast enough to act on it,
and in holding and settling money correctly across service boundaries --- through a
verification gate, a fee, an escrow hold, and a time-bounded dispute window --- when any
participant may fail mid-transaction. Docker keeps the local, CI, and hosted environments
identical, Render and Vercel remove deployment from the critical path, and Prometheus,
Grafana, and Jaeger make the distributed behaviour observable enough to evaluate against
the metrics in Section~10.
